## 1. Purpose

This document works through the technology stack we actually plan to build for: a **Looking Glass** holographic display, driven by a **Unity** application, with **Ultraleap-style infrared hand tracking** and **mid-air ultrasonic haptics** on top. It covers what each layer requires, how they fit together, what the team needs to learn, and the two delivery options we are weighing up.

The Nova/VX-lab-generic path is not being pursued because it does not describe the hardware we were actually introduced to.

## 2. Technology Stack Overview

The stack has four layers, and each one has its own requirements.

**Display layer — Looking Glass light-field display.** The Looking Glass is an autostereoscopic display: viewers see a true 3D image floating in a volume in front of the screen without needing a headset or glasses. The image is generated by rendering the same scene from many virtual camera angles at once, so the hardware needs a real graphics card behind it.

**Application layer — Unity.** Unity is a real-time development engine we use to build the interactive scene. It is not the delivery target; it is the tool we author in. The Looking Glass Factory ships an official Looking Glass Unity Plugin that hands Unity's rendered output to the display, and a companion Looking Glass Bridge service handles the connection to the physical device.

**Input layer — infrared hand tracking (Ultraleap).** A small infrared-camera module sits under or near the Looking Glass and tracks the user's hands inside the volume in front of the display. Ultraleap ships a Unity plugin that exposes joints, pinch, grab and pose detection, so game logic can respond to real hand movement.

**Haptic feedback layer — mid-air ultrasonic haptics.** A phased array of tiny ultrasonic transducers ("mini speakers") sits below the display and focuses inaudible pressure onto the user's skin. This creates the sensation of touching virtual objects mid-air, with no glove or controller. Ultraleap's STRATOS platform is the reference implementation for this, and it also has a Unity integration.

The technology decision is therefore no longer "which engine?" — it is "which layers of this stack do we commit to for the final experience?".

## 3. Technology Options Matrix

Because Unity, the Looking Glass and hand tracking are all effectively fixed by the lab and by what the demo showed, the real content/delivery decision is whether we ship the mid-air haptics layer as part of the final experience or leave it as a stretch goal. Both options are plausible; they trade different things.

| Area | Option 1 – Full stack (visual + hand tracking + haptics) | Option 2 – Reduced stack (visual + hand tracking only) |
|------|-----------------------------------------------------------|--------------------------------------------------------|
| Display | Looking Glass | Looking Glass |
| Game engine | Unity | Unity |
| Input | Ultraleap hand tracking | Ultraleap hand tracking |
| Haptic feedback | Mid-air ultrasonic haptics (Ultraleap STRATOS or equivalent) | None (visual + audio only) |
| User experience | User can "touch" and feel virtual objects | User sees and moves objects, but no tactile response |
| Extra hardware needed | Haptics array in addition to display and tracker | Display and tracker only |
| Extra SDK integrations | Ultraleap hand tracking plugin + Ultraleap haptics SDK | Ultraleap hand tracking plugin only |
| Development complexity | Higher — three coordinated subsystems | Lower — two coordinated subsystems |
| Failure modes | Any one of three subsystems can misbehave in a demo | Fewer moving parts, fewer surprises |
| Lab-time dependency | Higher — need lab access for every haptics test | Lower — hand tracking rigs are more portable |
| Best used when | The tactile sensation is core to the concept | The tactile sensation is a "nice to have" |

### Preliminary comparison

Option 1 is the closest to what we were shown in the demo, and it is the version that will feel most impressive to a first-time viewer because touching virtual objects mid-air is a genuinely novel sensation. The trade-off is that it depends on a specialised haptics array that we do not control, and it is the hardest layer to iterate on because it needs lab access, careful calibration, and a lot of physical testing.

Option 2 preserves the visual "wow" of the Looking Glass and the interactivity of hand tracking, but skips the fragile haptics layer. It is faster to build, easier to demo remotely on any Looking Glass, and easier to test outside the VX lab. It is a sensible fallback if haptics hardware turns out to be scarce, unreliable in our timeframe, or blocked by SDK/access issues.

### Preliminary recommendation

Aim for Option 1 (full stack) as the target experience, but design the game so that Option 2 is a working fallback rather than a broken version of Option 1. Practically, this means treating haptics as an *additive* layer over the visual + hand-tracking core, so that turning haptics off degrades gracefully rather than breaking the interaction. A small proof-of-concept in the first two sprints should confirm that both configurations run in the lab before we commit.

## 4. 3D Content and Asset Formats

Content for the Looking Glass is authored inside Unity as normal 3D scenes; the Looking Glass Unity Plugin handles turning that scene into the multi-view render the display needs. That means we can use the same asset formats Unity accepts natively — FBX, OBJ, glTF, DAE — and the standard modelling → export → import workflow applies.

### Proposed asset pipeline

3D modelling software → export as FBX (or glTF for lighter/simpler models) → import into Unity → set up materials and textures → position within the Looking Glass "hologram camera" volume → wire up hand interactions → test on the actual Looking Glass in the lab.

FBX should be the default interchange format because it is the most consistent handoff between modelling tools and Unity.

### Content considerations specific to Looking Glass

A few things that are not obvious from generic Unity work:

- The Looking Glass renders the same scene from many viewpoints simultaneously, so scene complexity has a bigger performance impact than on a normal monitor. Keep polygon counts sensible and avoid overly heavy post-processing.
- Objects that matter belong inside the *hologram camera volume* — the invisible box in front of the display where the 3D effect actually works. Anything outside that volume looks flat or clipped.
- Depth cues (subtle parallax between objects, careful lighting) matter more than for a regular screen, because they are what sells the "floating" effect.
- If the user is going to reach into the scene to touch things, the touchable objects need to sit at a physically reachable depth inside the volume — not just look reachable.

## 5. Software and Development Environment Requirements

Everyone on the team should be working with the same Unity version and the same SDK versions. Otherwise we will spend more time fixing environment mismatches than building the project.

Confirmed from vendor documentation:

- The latest Looking Glass Unity Plugin (4.0.0 Beta) targets **Unity 6** (specifically Unity 6000.0.39f1 through 6000.1.4f) with Universal Render Pipeline v17.0.4–17.1.
- The older Looking Glass Unity Plugin 3.2.8 supports **Unity 2021.3 or newer** if we need broader compatibility.
- The plugin requires **Looking Glass Bridge v2.0.9 or newer** running on the same machine as the Unity application.
- Looking Glass supports **Windows (with a dedicated GPU)** and **Apple Silicon Macs** for authoring and driving the display.
- Ultraleap's Unity plugin covers pinch, grab, pose detection, "physical hands" simulation, multi-device tracking and hand attachments, and integrates with XRI / MRTK3.
- Ultraleap's mid-air haptics stack (STRATOS) has a separate Sensation Designer / haptics SDK that plugs into Unity alongside the hand-tracking plugin.

### Recommended team setup

| Component | Choice |
|-----------|--------|
| Display | Looking Glass (model to confirm with VX lab) |
| Game engine | Unity 6 |
| Render pipeline | Universal Render Pipeline (URP) v17.0.4–17.1 |
| Looking Glass plugin | Looking Glass Unity Plugin 4.0.0 Beta |
| Looking Glass service | Looking Glass Bridge v2.0.9 or newer |
| Hand tracking | Ultraleap Unity plugin + supported Ultraleap tracker |
| Mid-air haptics (Option 1) | Ultraleap STRATOS + haptics SDK for Unity |
| Editor / IDE | Unity Editor + VS Code or Visual Studio |
| Source control | GitHub (Git) |
| Project management | Microsoft Planner |
| 3D assets | FBX preferred; glTF and OBJ where appropriate |
| Documentation | Master Document + project repository |
| Testing | Unity Editor for iteration; VX lab for hardware-in-the-loop testing |

Team rule: same Unity version, same URP version, same plugin versions across everyone's machines, wherever we can help it.

## 6. Browser and Web Delivery Requirements

The Looking Glass is not a web-delivered target. It is a physical display that needs the Looking Glass Bridge service running on the host machine, so a browser-only build is not a realistic delivery format for the final experience.

That said, a small **web build** could still be useful as a *demo/documentation aid* — for example, a flat, non-holographic Unity WebGL build of the same scene that assessors can open in a browser to see the interaction logic when they cannot get to the Looking Glass. This is optional and only worth doing if we have spare time near the end of the project.

For the actual holographic experience, the delivery target is a **standalone Unity build** running on the machine that drives the Looking Glass, with Bridge, the hand tracker and (Option 1) the haptics array all connected.

## 7. Hardware and Performance Considerations

Looking Glass performance depends on all four layers of the stack, not just the engine.

**Display side.** The Looking Glass renders the same scene from many angles per frame, so it is more GPU-heavy than a normal monitor showing the same scene. A dedicated GPU is required on Windows; Apple Silicon Macs are supported.

**Scene side.** Factors that matter most in practice:

- Polygon count of models in the hologram volume
- Texture resolution
- Number of lights and real-time shadows
- Post-processing effects
- Number of interacting objects per scene
- Animation complexity
- Scripts and physics interactions

**Input side.** Hand tracking cameras have their own frame rate and their own compute cost, plus a physical *tracking volume* — the region in front of the tracker where hands are actually recognised. Objects users need to touch must live inside both the display's hologram volume and the tracker's tracking volume.

**Haptics side (Option 1).** The ultrasonic array has its own *interaction volume*, typically smaller than the display volume. Haptic effects have to be authored against that constraint. The array also needs a clear line of sight to the user's hand.

### Proposed performance test

The prototype should include:

- A representative 3D scene that fits inside the Looking Glass hologram volume
- A few representative interactive objects
- The hand-tracking interactions the final experience will need (pinch, grab, hover)
- Lighting and materials close to the intended final look
- Any important animation or visual effects
- Under Option 1, one haptic sensation attached to one interactive object

The prototype then has to be tested **on the actual Looking Glass in the VX lab**, not just in the Unity Editor preview, because performance and depth perception on the real display are what we are actually optimising for.

## 8. Team Learning and Onboarding Requirements

This stack is new to most of the team, so an initial onboarding period is part of the plan rather than a nice-to-have.

### Developer learning

Developers should get comfortable with:

- The Unity Editor
- Scenes, GameObjects, components, prefabs
- Materials and textures
- Basic C# scripting
- Unity package management
- Universal Render Pipeline basics
- The Looking Glass Unity Plugin (hologram camera, quilt rendering, in-editor preview)
- Looking Glass Bridge (installation, device detection, calibration)
- The Ultraleap Unity plugin (hand rig, pinch/grab, physical hands, pose detection)
- The Ultraleap haptics SDK / Sensation Designer (Option 1 only)
- Build settings for a standalone Windows/macOS Unity build that talks to Bridge
- The Git-based project workflow

### UX learning

UX team members should understand:

- Looking Glass scene structure and the *hologram volume* concept
- The overlap between hologram volume, hand-tracking volume and haptic volume
- What interactions actually feel natural in a mid-air context (reach, pinch, push)
- Depth and parallax cues that make the 3D effect read well
- Placing UI so it is readable inside a holographic display (not the same as flat-screen UI)
- Accessibility considerations for a display that assumes a physically-present, standing user with two hands

### BA learning

The BA needs to know enough about the stack to write requirements that can actually be tested against the hardware. Each requirement should cover:

- User action (including which physical gesture)
- Expected system response (visual, and haptic if Option 1)
- Preconditions (hardware connected, hand in tracking volume, etc.)
- Constraints (hardware limits, safe interaction zones)
- Error and edge cases (hand leaves volume, tracker loses hand, haptic array offline)
- Acceptance criteria

## 12. Preliminary Recommendation

Based on the investigation so far, the Looking Glass + Unity + hand tracking + mid-air haptics stack is a solid technology choice for the project because it is the actual stack the VX lab supports and the one shown to us in the introductory demo.

The recommendation is:

- Commit to Unity 6 + Universal Render Pipeline as the development environment.
- Use the Looking Glass Unity Plugin plus Looking Glass Bridge as the display integration.
- Use the Ultraleap Unity plugin for hand tracking.
- Target **Option 1 (full stack, including mid-air haptics)** as the intended final experience.
- Design the game so that **Option 2 (no haptics)** is a working, non-broken fallback — meaning haptics is an *additive* layer on top of a fully playable visual + hand-tracking core.
- Do the first proof-of-concept in the VX lab as early as the schedule allows, so any lab-only surprises (Bridge version, tracker mount, haptics availability, calibration) surface in Sprint 1 rather than late in the project.

The final choice between Option 1 and Option 2 should not be made from documentation alone — it should be confirmed after the first hardware-in-the-loop prototype and after the VX lab team confirms haptics availability for the duration of the project.
